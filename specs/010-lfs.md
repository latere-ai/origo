# Git LFS

## Overview

Large files belong in object storage, not in packs. Origo implements the
LFS batch API and hands clients presigned URLs so bytes never pass
through a node.

## Current state

Spec 001 reserves `origo/repos/<id>/lfs/`. `latere.ai/x/pkg/s3` has
`PresignGet(key, expires)` and `PresignPut(key, expires, contentLength)`,
which signs `Content-Length` and nothing else. `internal/lfs` does not
exist and no route under `info/lfs` is served.

One item for the builder, before the upload action below can pin the
type: `PresignPut` gained a variadic `PresignOption` with
`s3.WithContentType(string)` in `latere.ai/x/pkg` v0.59.0, which adds
the header to the signed set, so a `PUT` with another type is refused
by the store the way one with another length is, and `s3test` verifies
the signed header the same way. The module pins v0.58.0, which has
neither; the builder bumps `go.mod` to v0.59.0 or later.

## Design

### Endpoints

`{repo}` is `r/{id}.git` or `{owner}/{slug}.git` as in spec 003.
Requests and responses are `application/vnd.git-lfs+json` in the shape
the LFS batch API fixes.

| Method | Path | Behaviour |
|---|---|---|
| POST | `/{repo}/info/lfs/objects/batch` | `{"operation": "download"\|"upload", "objects": [{"oid", "size"}], "transfers": ["basic"]}`, body at most 1 MiB (spec 012); action `read` for download, `write` for upload; answers each object with its action, or with no `actions` for an upload of an object the store already holds (Objects, below) |
| POST | `/{repo}/info/lfs/verify` | the `verify` action of an upload: `{"oid", "size"}`; action `write`, because it completes the upload; 200 when the object exists with that size, 422 otherwise. The check is the size alone, from one `HEAD` of `lfs/<oid>`; the hash is not checked, because the node would have to read the whole object to compute it, and the bytes never passing through a node is the point of the presigned transfer. An object whose bytes do not match its `oid` is what the client's own `git lfs` refuses on download |
| POST | `/{repo}/info/lfs/locks` | 501 `lfs_locks_unsupported` with the LFS body below carrying its sentence; every path under `locks`, whatever the method, answers the same |

### Objects

| Key | Content |
|---|---|
| `origo/repos/<id>/lfs/<oid>` | the object bytes, written by the client through the presigned `PUT` |
| `origo/repos/<id>/lfs/verified/<oid>` | `{"size", "at", "subject"}`, created by `verify` with `If-None-Match: *`; an existing marker is a success |

A `download` action is a presigned `GET` on `lfs/<oid>` valid 15
minutes, given only when `lfs/verified/<oid>` exists; otherwise the
object's `error` is 404. An `upload` action is a presigned `PUT` on
`lfs/<oid>` valid 15 minutes with `Content-Length` pinned to `size` and
`Content-Type` pinned to `application/octet-stream`
(`s3.WithContentType`), so the store refuses an upload of another size
or type; the action's `header` object carries `Content-Type:
application/octet-stream`, because the signature covers that header
and the LFS basic transfer sends exactly the headers the action names;
plus a `verify` action naming the endpoint above with the request's
token in its `header` object as `Authorization`. The `verify` action's
`href` is the request's own origin, the `Host` the batch arrived on
with the scheme of `X-Forwarded-Proto` or of TLS, and the repository
path the batch was asked on; it is not `ORIGO_PUBLIC_URL`, because the
client must complete the upload through whatever it reached the batch
through, a proxy in front of the node, the counting proxy of the first
criterion, or a node addressed directly, and a public URL would send
the verify request around it. Objects are content addressed by `oid`; identical objects are
stored once per repository and not across repositories. Presigned URLs
are signed against `ORIGO_S3_PUBLIC_ENDPOINT`, the bucket endpoint LFS
clients can reach, which defaults to `ORIGO_S3_ENDPOINT`.

An upload batch answers no `actions` for an object the store already
holds, the batch API's rule for an object the server has ("If a client
requests to upload an object that the server already has, the server
should omit the `actions` property completely", Git LFS batch API,
`docs/api/batch.md` in the `git-lfs` repository): an object is held
when `lfs/verified/<oid>` exists and names the declared size, read once
per well-formed object before the quota rule, so a client that pushes
twice uploads once and the quota counts the held bytes once, through
the `lfs/` listing. A marker naming another size is not the client's
object and the upload action stays. A malformed object inside a batch
is a per-object 400 with the `invalid_request` sentence: `oid` must be
64 lower-case hexadecimal characters, because it becomes a key under
the repository's prefix, and `size` must not be negative. A failure of
the store or the signer on one object is a per-object 503 with the
`storage_unavailable` sentence, so one bad object does not lose the
batch.

### Errors

The batch API carries its own error shape and the envelope of spec 003
is not used on these paths. A top-level failure is the HTTP status with
the LFS body `{"message": "<sentence>", "request_id": "<trace id>",
"documentation_url": "<url>"}`: `message` is the sentence of spec 003's
table for the matching code (400 `invalid_request` for a malformed or
oversized batch body, 403 `forbidden`, 404 `repo_not_found`, 413
`over_quota`, 429 `rate_limited`, 503 `authorizer_unavailable` when the
authorizer of spec 007 produced no decision, 503 `storage_unavailable`
when the bucket did), `request_id` is the request's trace id once spec
011 puts one on the request and a fresh UUID until then or when tracing
is off, and `documentation_url` is this
spec's URL in the repository,
`https://github.com/latere-ai/origo/blob/main/specs/010-lfs.md`. There is no `details` object in the LFS
shape, so the developer fields of spec 003 are not sent here. A
per-object failure is `"error": {"code": <status>, "message"}`. A
request without a valid token never reaches these paths: the verifier
of spec 007 runs in front of the whole application mux and answers 401
`unauthenticated` in spec 003's envelope with `WWW-Authenticate: Basic
realm="origo"`, which is what `git-lfs` reads, so the client behaves
the same and no route table sits in the middleware. The
three failures this spec produces are codes of `internal/contract`
like every other, with one sentence each rendered from
`contract.Sentence` (spec 021); the code names the row in the table
and is not on the wire, because the LFS shape carries the status and
the sentence and no code string:

| Code | Status | Message | Details |
|---|---|---|---|
| `lfs_object_mismatch` | 422 | The uploaded object does not match its declared size. | `verify` of an object whose stored size differs from the declared one, or that was never uploaded; the hash is not checked (the endpoint table says why); `oid` is the one the request named; the LFS shape carries no `details`, so the body is the sentence, `request_id`, and `documentation_url` |
| `lfs_object_not_stored` | 404, per object | This object is not stored. | a `download` action for an object without a `lfs/verified/<oid>` marker; `oid` is the batch object the `error` sits on |
| `lfs_locks_unsupported` | 501 | Locking is not supported. | every path under `locks`, whatever the method |

### Quota

The rule is spec 012's, one rule for a push and for a batch: a
repository's size is `size_bytes` of the newest index plus the bytes
under `lfs/`, and a write that would take that past the authorizer's
`quota_bytes` is refused. Before answering an `upload` batch the node
lists `lfs/` once with the delimiter `/`, paged by 1 000, which returns
the `lfs/<oid>` objects with their sizes and groups `lfs/verified/`
into a prefix, and sums the sizes; when the repository's size plus the
batch's sizes exceeds `quota_bytes`, the batch is 413 `over_quota`
with the LFS body above. Objects uploaded and never verified count,
because they hold bytes until spec 019's sweep removes them. `verify`
with a size that differs from the stored object's answers 422 and
deletes the object. The listing is summed on every upload batch; the
60 second cache per repository is spec 012's and lands with it.

`quota_bytes` for a repository-bound token (spec 007) is
`auth.DefaultQuotaBytes`, 53687091200, the default of spec 007's
table: such a token is decided by its scope and the authorizer never
sees it, and its claim set (`iss`, `aud`, `sub`, `act`, `repo`,
`scope`, `iat`, `exp`, `jti`) carries no quota, so no figure of the
authorizer's exists for it. Spec 012 replaces the default with the
authorizer's figure for the minting subject.

### Deletion

The purge of spec 004 removes `lfs/` with the rest of the prefix after
the hold. Spec 019's `stats` reports `lfs_bytes`.

## Not in this spec

Locks. Cross-repository deduplication. The `ssh` and multipart
transfer adapters. Garbage collection of uploaded objects never verified
(spec 019's orphan sweep).

## Acceptance criteria

- `git lfs push` and `git lfs fetch` round-trip a 500 MiB file through
  the stack's MinIO while the node receives under 1 MiB of request
  bytes, measured by a counting reverse proxy the test runs in front
  of `ORIGO_TEST_URL` and gives the client as its remote, so every
  byte and request the node receives passes through it and is
  counted, while the presigned transfers go to MinIO directly and are
  not; a forward proxy set through `http.<url>.proxy` is not used,
  because `git-lfs` does not honour a URL-scoped proxy and one
  strategy is enough; the client reaches
  MinIO at `http://localhost:30900`, the `ORIGO_S3_PUBLIC_ENDPOINT` of
  the ports table of spec 013 (proposed: `test/e2e`,
  `TestSlowLFSRoundTripBypassesTheNode`, in the `e2e-slow` job of spec
  013 because of the transfer's size).
- An upload whose stored size differs from the declared size is refused
  at `verify` with 422 carrying the `lfs_object_mismatch` sentence and
  the object is deleted (proposed: `internal/lfs`,
  `TestVerifyRefusesASizeMismatch`).
- A download batch for an oid without a `lfs/verified/<oid>` marker answers a
  per-object 404 with the `lfs_object_not_stored` sentence and one with the
  marker answers a presigned URL that serves the bytes (proposed:
  `internal/lfs`, `TestDownloadNeedsVerification`).
- An upload batch that would exceed `quota_bytes`, counting an uploaded
  but unverified object, answers 413 with the LFS body carrying the
  `over_quota` sentence, a `request_id`, and no `details` (proposed:
  `internal/lfs`, `TestUploadOverQuota`).
- A `PUT` to the presigned upload URL with another `Content-Length` or
  a `Content-Type` other than `application/octet-stream` is refused by
  the store (`pkg/s3/s3test` verifies the signature), one with both
  pinned values lands, and the upload action's `header` object names
  the pinned `Content-Type`; `s3test` reports a signature failure
  through `t.Errorf` as well as the 403, so the test starts its
  `s3test.Server` with a `testing.TB` wrapper that records `Errorf`
  instead of failing and asserts the recorded message beside the
  status (proposed: `internal/lfs`,
  `TestPresignedPutPinsLengthAndType`).
- `verify` asks the authorizer for `write`, and a batch body over 1 MiB
  is refused with 400 and the LFS body carrying the `invalid_request`
  sentence (proposed: `internal/lfs`, `TestVerifyIsAWrite`,
  `TestBatchBodyLimit`).
- Deleting the repository removes `lfs/` after the hold
  (`internal/wal`, `TestSweepRemovesOrphansAndKeepsWhatAnIndexNames`,
  extended with an LFS key).
- Every path under `locks` answers 501 with the LFS body and the
  `lfs_locks_unsupported` sentence (proposed: `internal/lfs`,
  `TestLocksAre501`).

## Outcome

Built on 2026-09-08 as `internal/lfs`, registered on the node and on the
contract stub of spec 013, with the presigned transfers signed against
`ORIGO_S3_PUBLIC_ENDPOINT` through `pkg/s3` v0.59.0. Every criterion has
a test in the tree, the round trip in spec 013's `e2e-slow` job, green
on main in run 34230344566.

| Criterion | Test |
|---|---|

| a stored size other than the declared one is 422 at `verify` and the object is deleted | `internal/lfs`, `TestVerifyRefusesASizeMismatch` |

Every LFS route is in the route sweep of spec 007 (`cmd/origod`,
`TestEveryRouteRequiresAToken`).

Divergences and interpretations, all kept:

- A request without a valid token answers spec 003's envelope, not the
  LFS body: the verifier middleware runs in front of the whole
  application mux and is one place for every surface. The status and
  `WWW-Authenticate: Basic realm="origo"` are what `git-lfs` reads, so
  the client behaves the same; moving the 401 into the LFS shape would
  put a route table in the middleware.
- A 503 on an LFS path carries the `authorizer_unavailable` sentence
  when the authorizer produced no decision, and `storage_unavailable`
  when the bucket did; the Errors section names both.
- The `verify` action's `href` is built from the request's own origin,
  not from `ORIGO_PUBLIC_URL`; the Objects section states the rule and
  why, and `TestVerifyHrefFollowsTheRequest` holds it.
- `request_id` is a fresh UUID on every failure until spec 011 puts a
  trace id on the request, as the Errors section says.
- The first build answered an upload action for every well-formed
  object, whether or not the store held it. The twelfth review round
  made the batch API's rule the design (Objects): a held object gets no
  `actions` and its bytes count once, held by
  `TestUploadSkipsAnObjectTheStoreHolds`.
- A malformed object inside a batch is a per-object 400 and a store or
  signer failure on one object a per-object 503, as the Objects section
  says.
- `quota_bytes` for a repository-bound token is `auth.DefaultQuotaBytes`
  until spec 012 replaces it, as the Quota section says.
- The `lfs/` listing is summed on every upload batch; spec 012's cache
  is not built here.
- `internal/lfs` renders its refusals itself rather than through
  `auth.Guard.Allow`, which writes spec 003's envelope; the guard grew
  `Decide`, which answers the decision behind an allow, and `Authorize`
  is now one line of it. That is what gives the batch `quota_bytes`.
